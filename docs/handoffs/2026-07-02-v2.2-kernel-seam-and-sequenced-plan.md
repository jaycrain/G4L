## Part A — Phase 0: the arc-configured kernel seam (design, for review)

**Goal.** Lift the onboarding-hardcoded stage machine (`applyStagedTurn`) into a generic *kernel* driven by an
**arc config**, so a second arc (Reconnect) can exist without forking the spine. **Onboarding becomes config #1.
All 53 staged + intent fixtures stay green — behavior identical.** This is a pure refactor, not a framework build,
and not Reconnect.

### What's generic (the kernel) vs. per-arc (the config)

**Kernel — arc-agnostic machinery we already have, just un-hardcoded:**
- the stage sequencer (advance through an ordered stage list)
- the reflect → confirm → advance loop (`awaitingConfirm`)
- the breathe-floor + escape pattern (draw out until rich OR member pushed past)
- model-judged depth (model signals ready; engine bounds with floor/cap + the verbatim-reflection gate)
- the runaway backstop (idle/ceiling stall detection)
- the capture-backstop pattern (model under-tags → engine captures in-stage)
- confirm-intent resolution (dispute / addition / done)
- the completion handoff (the seatbelt) + the no-verbatim-repeat guard

**Arc config — per-arc data the kernel reads:**

```ts
type StageMode = 'drawout' | 'administered';

interface StageDef {
  id: string;                       // 'gap', 'doors', 'idq', …
  mode: StageMode;                  // TWO-MODE — administered stages BYPASS the depth kernel (Jay's condition)

  // draw-out stages only:
  opener:        (c: Collected) => string;
  drawOutPrompt: string;                              // stage instruction appended to the system prompt
  isMaterialRich:(c: Collected) => boolean;          // the "already drawn out" escape
  pushedPast:    (msg: string, c: Collected) => boolean;
  depthFloor: number; depthCap: number;              // model-judged depth bounds
  reflect:       (modelText: string, c: Collected) => string;
  resolveConfirm:(msg: string) => 'dispute' | 'addition' | 'done';
  captureBackstop?:(msg: string, c: Collected) => Partial<Collected> | null;
  scopeGate?:    (corpus: string, c: Collected) => 'decline' | 'continue';   // OPTIONAL (onboarding fade-gate)

  // administered stages only:
  administer?:   (c: Collected) => AdministeredInstrument;   // verbatim items + scoring; NO draw-out, NO depth
}

interface ArcConfig {
  id: string;                       // 'onboarding' | 'reconnect'
  stages: StageDef[];
  onComplete: (c: Collected) => Turn;   // the card (onboarding) / the earned ceremony handoff (reconnect)
}

// kernel entry — replaces the hardcoded applyStagedTurn body:
function runArcTurn(arc: ArcConfig, state, history, memberMessage, model): Turn
```

Onboarding ships as `ONBOARDING_ARC = { id:'onboarding', stages:[identityStage, gapStage, reclaimStage], onComplete: card }`.
The current per-stage logic moves verbatim into those three `StageDef`s.

### Five design decisions to sign off on

1. **Two-mode is a first-class stage property.** `mode:'administered'` (IDQ / Grinta / Checkpoint) never enters
   the depth kernel — no floor/cap, no model-judged depth, no reflect-confirm. It delegates to the instrument
   component (administer verbatim items → score → advance). *This is the separation you asked for, enforced by type.*
   Phase 0 defines the `mode` field but the administered EXECUTION path stays a stub until Reconnect's §2c needs it
   (no building ahead).
2. **The scope gate (fade-gate / Decision-E decline) is an optional per-stage hook**, not baked into the kernel.
   Onboarding's gap stage supplies it; Reconnect stages won't. Keeps the kernel clean.
3. **Confirm-intent resolution is per-stage config** (`resolveConfirm`). Onboarding gap → `resolveGapConfirm`,
   reclaim → `resolveReclaimConfirm`. This is exactly where **Phase 2's model-signaled intent slots in** — the
   resolver's *implementation* swaps regex→model-signal; the config seam doesn't change.
4. **Per-stage scratch state.** The flat per-stage counters (`identityProbes`, `gapDepth`, `reclaimNudged`,
   `idleTurns`, `gapTurns`) are already sprawling. Proposal: a small `stageState: Record<stageId, object>` map so
   each stage owns its own counters. *This is the one place Phase 0 changes shape rather than just moving code —
   flagged for review. If you'd rather keep it flat for now, say so and I'll defer it.*
5. **Sized for the roadmap without building ahead.** The kernel runs *any* stage list, so future arcs (Rewire →
   Rebuild → Reclaim reflective beats, Cycle 2 variants) are **new `ArcConfig`s, not kernel changes**. Cycle 2 =
   a variant arc (lighter re-boarding) — same kernel. We add configs; we don't reopen the spine. That's the shape
   your roadmap implies, reached by config, not speculation.

**Phase 0 explicitly does NOT:** build Reconnect, touch the DB, add the administered execution path, or change any
observable behavior. Safety net = the 53 staged + intent fixtures, held green throughout; done incrementally
(extract one stage to config at a time, green between each).
